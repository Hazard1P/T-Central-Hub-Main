# Playable universe

Launch `/system` to fly. The default HUD has a toolbar and a compact speed, waypoint distance and bearing readout. Explore, Shipyard, Pilots and Settings open one panel at a time; `H` hides the HUD and `M` opens destinations. Sign in at the launcher or homepage; private discoveries belong to the account collection at `/profile`.

## Exploration

Launch starts near Earth in the enlarged, time-synchronized Solar System. The Sun, planets and Earth GEO beacon are normal destinations in the same universe; fictional deep-space destinations lie beyond the outer planets. Select one in Explore and cruise or fly there continuously. Travel never changes rooms or resets the ship. See [SOLAR-SYSTEM.md](SOLAR-SYSTEM.md) for global scale, deep-space assist, live UTC and Earth GEO.

- Fly with WASD/arrows, Space/R to rise, Shift/F to descend, Ctrl to boost and X to brake. Move the mouse to steer without holding a button; hold click or V to fire pulse cannons. Clicking optionally locks the pointer; Escape releases it. Touch devices have independent thrust, boost and Fire holds plus drag steering.
- Select a destination, then **Face destination** to orient without moving, or **Cruise to destination** to travel using bounded thrust. Steering or manual thrust cancels cruise. **Cancel cruise** returns manual control; automatic braking is enabled initially and can be changed in Settings.
- Cruise approaches a viewing point outside a planet, ring system or structure. Outer-world viewing points stay within the existing simulation bounds. The numeric guard encloses the outer Solar System; physical Solar bodies enforce safe surface boundaries. Enlarged black holes, Dyson structures and planetary surfaces also enforce shared clearances; solo private bodies use the same local rules.
- Discoveries record proximity to the selected landmark. Selecting a distant landmark does not count as a visit. Existing progression hydration and persistence remain in place.
- Halcyon, Pelagos and The Drift are defined in `lib/exploration.js`; rendering and navigation share those landmark definitions. Hub anchors and owned solo-world nodes are also selectable. Sealed system controls and unused relay actions are omitted.

## Shared flight

The hidden account-bound encounter is documented separately in [PRAYER-SEEDS.md](PRAYER-SEEDS.md), including its Unix epoch binding, account privacy and database migration.

Choose **Pilots → Shared universe**, enter the same room name on each device, or copy the invite link. Room names allow 1–64 letters, numbers, dashes and underscores. A room name is a rendezvous address, not an access-control secret. Guests can fly together. Pilots appear as ships, and the roster can set a waypoint to a pilot's last shared location.

`useSharedFlight` joins the authoritative WebSocket service using a short-lived ticket from the website. Controls stream at 20 Hz; server snapshots arrive at 10 Hz. Client prediction is reconciled against server positions, with a 300 ms prediction window. Guest identity comes from an opaque HttpOnly browser cookie; account identities come from verified Google/Steam sessions. The server controls elapsed simulation time, movement, hits and respawns. A full roster arrives each second while nearby pilots receive more frequent position updates.

All destinations share global coordinates and the chosen room. Flight between planets and deep-space objects never changes rooms or resets the ship. Shared flight waits for a real connection before enabling controls. Broken connections retain their flight for 30 seconds; joining the same identity elsewhere replaces the older connection. Explicit room/mode changes, emergency return and expired leases replace membership. Solo transforms stay separate.

Deploy the persistent service separately from Next.js; see [deployment](../SUPABASE_MULTIPLAYER_SETUP.md). The default service cap is 128 total pilots, enforced across named rooms. Account/economy records remain in protected Supabase storage. Live world transforms and combat scores are process-local and reset on restart. Local synthetic load results do not establish production hosting capacity.

## Visuals and verification

Planets use procedural surfaces, day/night lighting, atmospheric rims, ocean highlights and, in High mode, a separate cloud layer. Halcyon's rings have radial bands and a division. Instanced asteroids have deformed silhouettes, crater geometry and procedural mineral/grit textures. The fictional Drift comet has an icy nucleus, coma, dust plume and anti-solar ion tail. Local pulse hits on distant decorative debris produce brief cosmetic sparks. The Earth mining field supports shared depletion and regeneration. Auto mode uses Performance settings on touch/mobile devices; manual quality is saved locally. Bloom and dense clouds are disabled in Performance mode.

Run `node --test tests/*.test.mjs`, `npm run build`, `node scripts/verify-api-routes.mjs`, and `APP_SMOKE_BASE_URL=http://127.0.0.1:3000 node scripts/verify-pages.mjs` against a running build. `node scripts/verify-realtime-population.mjs` checks the live service with 128 synthetic clients. With the explicit legacy HTTP transport, `APP_SMOKE_BASE_URL=http://127.0.0.1:3000 node scripts/verify-exploration.mjs` tests connect/state/disconnect routes with two independent guest cookie jars in a temporary room, then releases those sessions. Flight tests cover cruise convergence, safe viewing points, batch parity, replay rejection, server-time limits, room isolation and authenticated disconnects. Browser verification should include two independent guest contexts, movement visibility, room switching, solo isolation, reconnects, HUD shortcuts, text input and touch releases.

## Ship weapons

Pulses appear immediately in solo/shared flight. Shared shots are accepted only for a valid session, at most every 200 ms, using the authoritative ship position and a finite normalized aim vector. They travel at 64 u/s relative to the firing ship and expire after 2.2 seconds. Server clients cannot choose a projectile origin or claim hits. Shared combat gives ships 60 shield and 100 hull; pulses deal 20 damage after server collision checks. Shields recharge at 6 points/second after five seconds without firing or taking damage. Hull repairs are free and automatic at 8 points/second in the Earth service shell (outside the surface, within 4.2 Earth radii, at or below 8 u/s), with the same combat delay. They offer no invulnerability. The compact HUD reports recovery or critical hull; Shipyard explains both systems. Shield impacts have a blue vignette and hull impacts a red one. Spawn protection lasts five seconds and ends on firing. Destruction records a session kill/loss, discards carried ore, and returns the ship to Earth after five seconds. There is no currency reward for combat. Mining in the Earth field uses its own server-checked economy endpoint; distant rock-hit sparks are cosmetic; lower quality clients may render fewer distant rocks. Account-bound Prayer Seed data is never part of these packets.

Phone controls support simultaneous captured pointers. Releasing or cancelling one finger leaves other held controls active. Opening a panel, hiding controls, switching sessions or losing focus clears held flight inputs. Phone Auto quality bounds pixel ratio and debris density and disables bloom. Browser emulation validates interaction/layout, but physical iOS Safari and Android device performance still needs a device check.

## Sound

Ship firing plays a short synthesized pulse synchronized with local shots. A layered, low-frequency universe hum runs quietly during active flight. Settings → Sound offers separate firing-effects and hum sliders plus mute; defaults are 45% effects and 3% hum. Preferences stay on this device under `tcentral_audio_v1` and are independent of account or payment records.

The Web Audio graph starts after a tap/key press, pauses when the tab is hidden or shared flight disconnects, and closes on leaving the simulation. Zero hum disables the hum completely; mute suspends audio processing. Pulse voices are bounded and released after each shot. No audio downloads or third-party sound licenses are required. Browsers without Web Audio keep flight available and disable sound controls. Phone browser emulation is checked; physical iOS/Android audio routing still needs device validation.

## Distributed cosmic map

`lib/cosmicLayout.js` supplies static star, black hole and Dyson coordinates, shared by rendering, waypoints and gravity. Most cosmic anchors are ten times farther from spawn than the original layout; the Sun has its own distant global center. Solar body positions come from `lib/universeFlight.js` and live ephemerides. The nearby fictional worlds and account-bound Prayer Seed encounter retain their locations. The camera may change its rendering origin, but the ship's global position and multiplayer room remain unchanged.

## Mining and ship upgrades

The launch desk has one account panel and direct **Join shared flight** / **Fly solo** actions. Its heading is capped at 44px on desktop and 32px on phones. Unavailable login providers show a configuration message; session and auxiliary support requests resolve independently. Transient refresh failures retain the last verified account and offer a retry. Both providers use the configured canonical `APP_URL` (or `NEXT_PUBLIC_APP_URL`); callbacks must be registered at that exact origin. Provider switching signs out the previous provider, keeping their histories separate.

Open **Shipyard** in a shared flight. Choose **Fly to mining field**, then **Approach nearest rock** or maneuver manually to a rock within 180 units and brake below 25 u/s. Aim and fire or use **Mine asteroid**. Every rock has 3 integrity; the mining laser starts at 1 damage with a 700ms cooldown. Each rock yields 4–7 ore in total, subject to free cargo space, and regenerates 45 seconds after depletion. Every successful hit immediately loads the ore unlocked by the integrity it removes: a basic three-hit rock with 7 ore pays 2, 2, then 3 ore. Pilots mining together each keep their own hit rewards; the finisher does not receive the whole rock. Upgraded lasers receive only the remaining yield, and receipt replay never awards a hit twice. Ore beyond free cargo space is discarded. All clients see the same depletion state for their room. The nearby field uses procedural crater and mineral materials at both quality levels, with exposed orange fracture seams as shared integrity falls. The cargo readout confirms ore pickups, and Shipyard shows rock integrity; distant decorative debris remains cosmetic.

Choose **Fly to Earth** or fly manually within 4.2 Earth radii, outside the surface, and brake below 8 u/s. **Unload** pays 10 game credits per ore. The initial hold has 20 capacity. Cargo upgrades add 15 capacity per level for 120/240/480 credits; mining laser upgrades add 1 damage per level for 150/300/600 credits. Each has 3 levels. Install upgrades at Earth, then repeat the trip. The small cargo/credit button opens Shipyard; detailed controls stay in the panel.

Wallets use the verified provider and account ID. Guest training wallets belong to their opaque browser cookie and are not merged into a later account. Credits and installed upgrades survive flights; **carried ore is flight-bound and discarded on a fresh session, room change or emergency return**. Rejoining an existing live flight preserves its position. Game credits are separate from legacy client progression, voluntary contributions and undefined VIP plans; they cannot be redeemed or purchased here.

Deployment: apply `supabase/migrations/20261022_ship_economy.sql` after the existing multiplayer and simulation-event migrations, then apply `supabase/migrations/20261024_cooperative_mining.sql`, and set `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` and a stable `SESSION_SECRET`. Wallet, shared-rock and receipt changes run in one service-only database transaction with row locks and receipt replay protection. Flight and audit tables are also server-only because they contain session credentials. The game service streams sanitized WebSocket snapshots; raw anonymous Realtime subscriptions to these tables are intentionally unavailable. Do not expose the service role key to the browser. Without the migration/configuration, production shows an explicit economy-unavailable message while free flight remains usable. Non-production local development may use the ignored `data/ship-economy.json` file.

Verification includes pure rule/repository tests, a PostgreSQL-compatible PGlite migration and role-permission check, and production API/browser tests using a local database REST fixture. OAuth upstream responses are mocked for callback regression checks; live Google/Steam round trips and real device performance require deployment verification. This includes a runnable dedicated game service with combat, account persistence and shared mining. Hosting, credentials and production capacity still require deployment validation.

The cooperative-mining migration retains existing wallets, shared rocks and action receipts. Previous receipts replay unchanged; already-partially-mined rocks are not retroactively paid for hits made under the old rules. Deploy the migration before the matching website/game-service release. Hull repairs require the updated persistent game service, not the legacy HTTP adapter.

## Shared physics engine

Flight now uses shared Newtonian planetary gravity, double-precision RK4 substeps, vacuum coasting, swept celestial contacts with full hull clearance and authoritative ship-to-ship impulses. Cannons, visual impacts and mining paths use the same contact primitives; incompatible website/server physics releases show a reload message. Disable automatic braking in Settings to coast; X/Brake applies thrust to slow down. Settings → Flight physics shows local gravity and escape speed. The same physics drives legacy movement interfaces and client/server prediction. See [physics architecture and limits](PHYSICS-ENGINE.md).
